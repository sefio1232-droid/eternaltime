# Database And Catalog Foundation Implementation

This document records implementation decisions introduced by the database and catalog foundation phase. It does not replace `DATABASE.md`; it makes exact migration-level choices explicit.

## Migration Responsibilities

- `20260705010000_foundation_extensions.sql`: PostgreSQL extension setup and shared immutable normalization helpers.
- `20260705011000_identity_roles.sql`: `profiles`, auth profile trigger, `roles`, `user_roles`, and server/RLS role lookup helpers.
- `20260705012000_catalog_dimensions.sql`: controlled catalog dimensions and controlled attribute definitions/options.
- `20260705013000_catalog_identity.sql`: Brand hierarchy, `watch_references`, relation traits, controlled attribute values, and search document foundation.
- `20260705014000_commercial_state_and_media.sql`: delivery estimate foundation, inventory states, offers, price history, inventory events, and catalog image metadata.
- `20260705015000_rls_policies.sql`: RLS enablement and public/admin policy boundaries.

## Role Model

Initial roles are `customer`, `admin`, `catalog_manager`, `content_manager`, and `order_manager`.

Admin access is now sourced from `roles` and `user_roles`; it is not inferred from email. Admin route guards fail closed when Supabase is unconfigured, a user is unauthenticated, or role retrieval fails.

Initial administrator assignment is an operational database action: create or identify the Supabase Auth user, then grant the `admin` role in `user_roles` by user ID. Do not hardcode an email in application code.

## Reference Normalization

Manufacturer reference normalization is deterministic:

- Unicode NFKC normalization.
- Uppercase.
- Remove separators and punctuation.
- Preserve alphanumeric characters.
- Reject empty normalized values.

`watch_references.reference_code_display` preserves the original manufacturer-facing value. `reference_code_normalized` is generated by the database and enforces uniqueness with `(brand_id, reference_code_normalized)`.

## Reference Slugs

The initial canonical reference slug is derived from the normalized manufacturer reference and lowercased for URL safety. The database stores `slug` separately so a published URL can remain stable if a display reference is corrected later. Silent collisions are prevented by `(brand_id, slug)`.

Canonical watch URL remains:

```text
/watches/{brandSlug}/{referenceSlug}
```

## First-Class Watch Fields

Implemented first-class fields on `watch_references` include:

- Movement type and movement/caliber references.
- Case material, coating material, shape, color, dial color, crystal, strap/bracelet material, clasp type.
- Case diameter, width, lug-to-lug, thickness, lug width, weight, water resistance.
- Common functions as booleans: date, day-date, GMT, chronograph, tachymeter, world time, alarm, stopwatch, timer, moon phase, rotating bezel.
- Brand and production country codes.
- Data confidence and separate reference lifecycle status.

## Normalized Dimensions

Controlled dimension tables include movement types, movements, materials, colors, crystal types, case shapes, clasp types, styles, use cases, and watch functions.

Styles, use cases, and functions attach to `watch_references` through join tables. Style and use-case joins include `score` with a `0..1` constraint so Collection Intelligence can later use weighted traits without uncontrolled EAV.

## Controlled Attributes

The controlled attribute foundation consists of:

- `attribute_definitions`
- `attribute_options`
- `watch_reference_attribute_values`

Definitions require a key, scope, explicit value type, status, and admin-reviewed metadata. Values use typed columns and enforce exactly one stored value. Frontend code must not create definitions automatically.

## Commercial State

`catalog_offers` is separate from factual reference identity. It owns offer status, offer kind, condition, optional SKU, current/previous price in integer minor units, currency, inventory state, delivery estimate, visibility, and purchase limit.

Price history is in `offer_price_history` with one current row per offer enforced by a partial unique index. Inventory changes are in `inventory_events`. Delivery estimates are modeled as data records only; no provider integration exists.

## RLS Summary

Public reads are allowed only for public-safe records:

- Published brands, Brand Collections, Brand Lines.
- Active/archival Watch Models.
- Published/archival Manufacturer References.
- Active controlled dimensions.
- Visible active/coming-soon/on-request offers.
- Published catalog images.

Writes are restricted to authenticated users with `admin` or `catalog_manager` roles for catalog/commercial tables. Role grants are restricted to `admin`.

## Database Types

Generated Supabase database types are not hand-written. When a local Supabase runtime is available, generate them with:

```bash
npm run db:types
```

This writes `src/lib/supabase/database.types.ts`. Application domain types remain separate from generated row types and are introduced only where transformation is useful.

## Integration Validation

The repository contains pure-domain and migration-shape tests. Real constraint/RLS execution still requires a local Supabase/PostgreSQL runtime. Run Supabase migration validation locally when the CLI/runtime is available.

## Catalog Source Import Pipeline

The local catalog source intake pipeline is implemented outside the public UI and outside database mutation paths. It lives under `src/modules/imports/catalog/` and follows the staged import contract:

```text
raw source discovery -> source detection -> parse -> normalize -> merge sources -> validate -> image audit -> staged preview -> import apply plan
```

Important implementation decisions:

- Source detection is content-based and filename-independent.
- `watch_references` remains the canonical concrete watch entity.
- No `watch_variants` model is introduced.
- Manufacturer reference normalization reuses the catalog domain function.
- The generated `ImportApplyPlan` is a proposal only; this phase does not write production catalog rows.
- `publicPriceCandidate` uses the maximum valid recognized RUB source price for the normalized watch row.
- Other source price values remain internal import provenance.
- `Разница` is explicitly excluded from public price selection.
- Image candidates are manifest entries only; no Supabase Storage upload or `public/` copy occurs in this phase.
- The quality pass classifies source conflicts by impact: content draft conflicts are non-blocking, identity conflicts require review, and compatible duplicate rows merge as the same identity.
- Image manifest rows attach only to existing product identities and never create standalone product candidates.
- `catalog-review-queue.json` is generated for future manual review tooling; no admin UI exists in this phase.
- Controlled database apply is implemented as a separate preview-driven boundary with dry run, explicit confirmation, database preflight, and generated image upload plan.
- Records with unavailable reliable Manufacturer Reference are classified as `intentionally_skipped_missing_reference` and are excluded from `watch_references`, offer, price, and image upload apply plans.

Detailed source-data rules are recorded in `docs/CATALOG_SOURCE_DATA.md`. Quality-pass rules are recorded in `docs/CATALOG_IMPORT_QUALITY.md`. Controlled apply rules are recorded in `docs/CATALOG_APPLY.md`.

## Catalog Read Experience

The public catalog read experience now uses a dedicated Catalog Read Repository boundary:

```text
Catalog data source -> Catalog Read Repository -> Catalog Read Models -> Server Components / UI
```

The current development source is an explicit preview adapter over generated import artifacts. It is selected with `CATALOG_READ_SOURCE=preview` and is allowed only outside production. Production does not fall back to preview data when the database repository is unavailable or empty.

Public read models expose only public catalog presentation data: Brand, Brand Collection, Watch Model, Manufacturer Reference identity, canonical slugs, public price, public specifications, image presentation sources, and sibling Manufacturer References sharing the same Watch Model concept.

They deliberately exclude import provenance, validation issues, raw source rows, source SEO drafts, internal price observations, source CNY cost, and source difference / `Raznitsa` values.

Implemented public routes:

```text
/watches
/watches/{brandSlug}
/watches/{brandSlug}/{referenceSlug}
```

`/catalog` redirects to `/watches` to avoid duplicate canonical catalog pages. The canonical watch route remains `/watches/{brandSlug}/{referenceSlug}`.

The dev-only image resolver serves local ZIP images through opaque manifest keys. It does not expose filesystem paths, arbitrary ZIP entries, source Excel/ZIP files, or non-eligible record images. The resolver is disabled in production.

Detailed read-experience rules are recorded in `docs/CATALOG_READ_EXPERIENCE.md`.
